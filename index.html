Distributed RL infrastructure across an HPC cluster and the cloud

SSAIL, UIUC · Jan 2026 – present · advisor Prof. Minjia Zhang
Problem
Run and benchmark agentic RL (TRL AsyncGRPO, TorchForge) on official SWE-Bench Verified tasks, with training on NCSA DeltaAI and the Dockerized evaluation environments on AWS EC2. Two clusters, two schedulers, one experiment.
Hard part
An early result showed one framework clearly outrunning the other. It was an artifact: the two runs had been given asymmetric GPU placement. Left uncaught, that number would have steered the project.
What I did
Profiled both frameworks on step latency, memory, utilization, and placement traces; normalized placement and re-ran matched experiments. Deployed Qwen3.5-4B with FSDP2 (2-GPU BF16 training) and vLLM on 4× RTX PRO 6000 Blackwell, then traced an NCCL policy-weight sync hang at the first update to the source, ruling out inference DP and the 1 GB packed-transfer limit with controlled A/B topology tests.
Result
A corrected comparison, a reproducible pinned stack (PyTorch/CUDA/vLLM/TRL with state moved off ephemeral NVMe), and a working DeltaAI→EC2 execution path for SWE-Bench workloads.
Benchmark scripts on GitHub lab infrastructure is otherwise private

Adaptive LLM inference runtime

independent project · Python, PyTorch, vLLM, CUDA · Llama models, ShareGPT prompts
Problem
Autoregressive decoding pays a full forward pass per token even when the model is nearly certain about the next several. Speculative approaches help, but unsafe multi-token transitions degrade output quality.
Hard part
Deciding when a multi-token step is safe. Single confidence signals were unreliable; the runtime combines entropy, margin, energy, and agreement signals, and profiles verification and KV-cache behavior to characterize the transitions that go wrong.
What I did
Built a decoding runtime that routes between single- and multi-token generation per step, plus the profiling to find where it broke. Batched inference and LLM-as-judge evaluation across 5,000 generations.
Result
2.3× fewer decoding steps and 28% lower long-form latency against the single-token baseline. Evaluation time went from 90 s to 3.3 s per sample (27×) by batching, which is what made the 5,000-sample sweep feasible at all.
Related: KV-cache tiering for multimodal RAG serving (GitHub) runtime code not yet public

Production billing and subscription services at telecom scale

Oracle · Batelco Telecom, PPC Retail India · Jul 2023 – Jan 2026
Problem
Subscription, billing, and account workflows for a telecom operator: 10M+ transactions a day across 8 Java/Kotlin Spring Boot services, 20+ REST APIs, and Kafka fan-out to 12+ downstream integrations. The failure that matters is charging someone twice.
Hard part
Throughput collapsed under load and nobody could say why. Prometheus traces showed gRPC HTTP/2 stream exhaustion and connection-pool saturation on the path to the 5G core, not the application code everyone was staring at.
What I did
Tuned Istio/OCNE connection pools and service configuration; designed saga recovery plus Redis idempotency keys so retries are safe by construction; built retry-and-dedupe Kafka pipelines; reworked SQL/JPA access paths over 300M+ monthly records. Also led a 4-person team shipping a production RAG assistant (LangChain, Cohere, Neo4j) for 500+ engineers.
Result
+37% throughput and −12% P95 latency on the gRPC path; 99.95% of transactions completing correctly under concurrent load; +35% Kafka delivery throughput with zero duplicate-charge incidents after rollout; −20% peak-cycle database latency. The assistant cut hallucinations 41% and ticket-resolution time 33%.
client systems; no public code. Recognition: Above and Beyond Award, Pat on the Back Award.
